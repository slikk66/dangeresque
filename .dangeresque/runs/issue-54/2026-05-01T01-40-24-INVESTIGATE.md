## 2. Replace-whole-line vs replace-just-number

**Recommended: replace the whole `Files: ...` line.**

Rationale:

1. Workers append free-form trailers after the count: `(... NEW)`, `(... DELETED)`, `; 1 commit (abcdef)`, `, uncommitted`, `— 248 insertions / 372 deletions`, `(..., +334 lines)`. These trailers can also drift. Partial replace (count only) leaves them intact, so the reviewer's claims-check still has surfaces to mismatch — the fix would incompletely close the failure class.
2. The body's "Files Changed" section is the spec'd home for filename-level context (`worker-prompt.md:86`: "The rest of the file follows with full details"). The SUMMARY's `Files:` line earns its keep by being deterministic, not narrative.
3. Whole-line replace is one regex (`/^Files:.*$/m` within the parsed SUMMARY block), independent of how many parenthetical clauses or punctuation styles the worker improvised.
4. Variants like `Files: 10 new + 2 edited (...)` (issue-23) lack an aggregate `N changed` count — partial replace would have nowhere clean to inject. Whole-line replace handles it uniformly.

Cost: worker context like `(read-only investigation)` is lost. Acceptable — the body's Status line and free text already convey that. Existing consumer `formatRunOneLiner` at `src/worktree.ts:341-348` only matches `/Files:\s*(.+)/` for display and is compatible with either form.

## 3. Canonical line format

**Recommended primary: `Files: N changed (X added, Y modified[, Z deleted])`**

Where:
- `N` = output of `git diff origin/main --name-only | grep -v '^\.dangeresque/runs/' | wc -l` (matches review-prompt.md:43 exactly).
- `X / Y / Z` = bucketed counts from `git diff origin/main --name-status` (A=added, M=modified, D=deleted; treat R as M; treat C as M). Counted from the same path-filtered set.
- Drop zero buckets. Drop the parenthetical entirely when `N=0`.

Concrete examples:
- `Files: 0 changed`
- `Files: 23 changed (7 added, 16 modified)`
- `Files: 7 changed (5 modified, 2 deleted)`
- `Files: 2 changed (2 modified)`

Deleted bucket: worth including. Deletions are real and informative (e.g. "removed dead config"); dropping them would mask substantive changes.

**Minimal alternative:** `Files: N changed`. Defensible if the team prefers no parenthetical at all — fewer claims, fewer comparisons, simplest possible canonical. The breakdown form costs ~5 lines of bucketing logic for the readability gain.

## 4. Modes to normalize

**Recommended: normalize uniformly across all modes.**

Rationale:

1. Single code path; no mode-specific branching; the existing scope check (`cli.ts:471-504`) is mode-agnostic.
2. Read-only modes drift too — issue-28 and issue-29 both have INVESTIGATE workers writing `Files: 1 changed (.dangeresque/runs/...)` because they counted their own auto-committed run-result file. Uniform canonical normalization auto-corrects this (the canonical query already excludes `.dangeresque/runs/`).
3. Reviewer is skipped for INVESTIGATE/VERIFY (`cli.ts:532-536`), so normalizing those modes has no immediate review-verdict effect. But it surfaces accidental scope expansion: an INVESTIGATE worker who edited a file would get `Files: 1 changed` instead of `Files: 0 changed (read-only)`, exposing the violation to humans reading the artifact and to stats tooling.

## 5. JSON artifact field

**No `files_changed_count` first-class field exists.** `RunArtifact` interface at `src/artifact.ts:45-73`. Closest existing data:

- `lifecycle_events[].data.changed_files` — set at `cli.ts:498-501` from the scope check. Already canonical (git-derived). Buried in event metadata.
- `scope_violations: string[]` (`cli.ts:496`) — only files NOT mentioned in the issue body. Subset, not total.

The `.md` `Files:` line is the only top-level worker-facing source-of-truth, and it is hand-typed.

**Recommendation: add `files_changed_count: number` as a first-class `RunArtifact` field.** Bump `ARTIFACT_SCHEMA_VERSION` from `"2"` to `"3"` per `artifact.ts:7` ("additive changes require bumping ARTIFACT_SCHEMA_VERSION"). Populate from the same canonical count used to rewrite the `.md`. Honors the "fold into the same fix" guidance: stats tooling (`src/stats.ts`) gets a clean field instead of re-parsing markdown, and the .md and JSON cannot diverge.

If the team prefers to keep the schema unchanged, leaving the count only in the .md SUMMARY line is workable but means stats tooling that wants this number must read the .md. Schema bump is the cleaner fix.

## 7. Chronological position

Tracing `cli.ts:380-602`:

1. `cli.ts:396-403` — `runWorker` returns; worker has committed its `.md` (via `runner.ts:777`'s call to `commitArchiveFile`).
2. `cli.ts:423-468` — hard-stop on worker failure (early `process.exit`).
3. `cli.ts:471-504` — post-worker scope check (`git diff ${diffBase}...HEAD --name-only`, filters `.dangeresque/runs/`). `changedFiles` computed here.
4. `cli.ts:506-529` — rebase worktree onto `origin/main`. On failure, `git rebase --abort` restores prior state.
5. `cli.ts:531-552` — review pass (skipped for INVESTIGATE/VERIFY).
6. `cli.ts:555-576` — post summary comment to GitHub.
7. `cli.ts:578-595` — `finalizeArtifact` (writes JSON, commits via `commitArtifactJson`).

Issue's tentative position: "AFTER worker commits the .md but BEFORE rebase."

**Challenge in writing — recommend AFTER rebase, BEFORE review.**

Rationale:

- The reviewer runs `git diff origin/main` AFTER rebase (`review-prompt.md:7,13`). For the canonical count to match the reviewer's check exactly, it must be computed from the SAME post-rebase tree.
- Edge case the pre-rebase position misses: if `origin/main` itself added a file the worker also added, rebase deduplicates cleanly without a conflict, and the post-rebase `git diff origin/main --name-only` shows ONE FEWER file than the pre-rebase `git diff origin/HEAD...HEAD --name-only` did. Pre-rebase canonical count would over-count, re-introducing the false-REJECT failure mode this issue is meant to eliminate.
- If rebase fails and `git rebase --abort` restores prior state (`cli.ts:520`), the reviewer's `git diff origin/main` and the canonical count would BOTH operate on the un-rebased branch — they still agree (both seeing the same phantom diff). Robust.
- Cost: one extra `git diff --name-only` invocation. Trivial (the tree is already on disk; just an `execSync`).

**Code shape:** insert a new block at `cli.ts:530` (after the rebase try/catch at 508-529, before the review block at 532). Run `git diff origin/main --name-only` (and optionally `--name-status` for the breakdown), filter `.dangeresque/runs/`, compute the canonical line, rewrite the `.md`'s SUMMARY block, commit a new revision via the new helper.

If the team strongly prefers the issue's pre-rebase position, the implementation can reuse `changedFiles` from `cli.ts:477-484` (saves the extra git invocation). Trade-off: marginal cost saving for losing post-rebase robustness against the parallel-merge edge case. I'd default to post-rebase.

## 8. Reviewer prompt adjustment

**Recommended: silent overwrite is sufficient. No reviewer-prompt change required.**

The reviewer prompt at `review-prompt.md:43` already does the right thing:

> File count integrity: Run `git diff origin/main --name-only | grep -v '^\.dangeresque/runs/'` and count the results. Compare against the `Files:` line in `<!-- SUMMARY -->`. If they don't match, this is an automatic FAIL.

With canonical normalization, those two values are derived from the SAME query (same flags, same filter) — they cannot mismatch by construction. The "automatic FAIL" semantics stay intact and continue to catch the actual concealment scenarios (a worker who somehow edits the .md AFTER our canonical rewrite, or a CLI bug that fails to inject).

Optional belt-and-suspenders polish: amend `review-prompt.md:43` with a footnote like "the `Files:` line is dangeresque-canonical (rewritten by the CLI to match this exact diff query); a mismatch indicates a tool bug, not a worker concealment." Documentation polish, not behavior change. Skip if minimizing scope.

## 9. Failure-mode behavior

**Recommended: warn-and-degrade, never fatal.** Slightly louder than the existing scope check (which silently swallows everything at `cli.ts:502-504`).

Specifically:

- `git diff` fails (detached HEAD, no upstream, repo corruption): log `console.warn("⚠️  Could not normalize SUMMARY Files: line: <reason>. Reviewer will see worker's self-report.")`, skip rewrite, continue.
- SUMMARY block missing or malformed in the .md: log a warning, skip rewrite, continue. The reviewer's claims-check has its own "no Files: line" handling.
- File rewrite or commit fails: log a warning, continue. Same fallback.

In every failure case, the worker's hand-typed line passes through unchanged and the system reverts to today's behavior (false-REJECT possible, run otherwise valid). Never block review, never fail the run.

Why louder than the scope check? The scope check is advisory; the rewrite is THE feature being added. Silent failure across many runs would be invisible. Recommend logging via `builder.recordEvent("summary_normalize_failed", { reason })` so post-run stats can detect chronic failures over time.
