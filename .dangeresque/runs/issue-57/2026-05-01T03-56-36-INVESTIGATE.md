## Restating the problem

Two distinct leakage vectors, both rooted in the same architectural decision (commit artifacts so they ride normal git merge into main):

1. **On-disk leak** — `.dangeresque/runs/issue-<N>/<timestamp>-MODE.md` (and `.json` sibling) is committed in the worktree (`commitArchiveFile` at `src/runner.ts:103-112`, `commitArtifactJson` at `src/artifact.ts:395-407`) and brought into `main` via `git merge` (`mergeWorktree` at `src/worktree.ts:456+`). Once a project pushes `main` to a public origin, every run's full body — file paths, code snippets, internal reasoning, occasionally credentials in error logs — lands in the public history. `init.ts:163-174` actively *removes* any legacy `.dangeresque/runs/` entry from `.gitignore`, so the leak is by design today.

2. **GitHub comment leak** — `postRunComment` (`src/runner.ts:928-972`, called from `src/cli.ts:447` failure path and `src/cli.ts:575` success path) reads the entire artifact `.md` and posts it verbatim as an issue comment. Anyone with read access to the issue (everyone, on a public repo) sees the full investigation/implementation reasoning, including code snippets and file paths the worker touched.

The issue body says "keep the core workflow the same" — so the proposals below preserve: worker writes artifact in worktree → reviewer reads same file → human runs `dangeresque merge` → next worker on same issue can read prior runs → `dangeresque results` / `dangeresque stats` keep working.

## What relies on artifacts being in git today

Mapped from the codebase so each proposal can be evaluated against the real coupling:

- **Reviewer pass** reads the artifact at `<worktree>/.dangeresque/runs/issue-N/<timestamp>-MODE.md` (`buildReviewPrompt` in `src/runner.ts:479-501`). Only the worktree filesystem is touched — git involvement is incidental.
- **Worker prompt** tells the next worker "Prior runs … live at <runsDir>/" (`buildTaskPrompt` in `src/runner.ts:329-351`). Workers branch from `origin/HEAD`, so they only see prior runs if those runs are on `origin/main`. This is the single hardest dependency — without git tracking, prior-run history vanishes for new workers.
- **`dangeresque results <branch>`** reads from worktree (`getWorktreeResults` in `src/worktree.ts:727-819`).
- **`dangeresque results --issue N`** reads from project root after merge (`getArchivedResults` in `src/worktree.ts:824-868`).
- **`dangeresque stats`** scans `<projectRoot>/.dangeresque/runs/**/*.json` (`gatherArtifacts` in `src/stats.ts`).
- **Scope check** in `cli.ts:485` and **summary normalize** in `src/summary.ts:48` filter out `.dangeresque/runs/` paths from diff counts — assumes runs *are* in the diff, has to flip if they're not.
- **Reviewer prompt** says "EXCLUDE any path under .dangeresque/runs/ — those are auto-committed artifacts" (`runner.ts:497`) — same flip required.

## Proposals — On-disk artifact leak

### Proposal A1 — gitignore + side-channel copy on merge (mirrors `.dangeresque/sessions/`)

**The change:** add `.dangeresque/runs/` to `.gitignore` (and stop `init.ts:159-174` from stripping it). Worker still writes to `<worktree>/.dangeresque/runs/issue-N/...`. Drop the `commitArchiveFile` and `commitArtifactJson` calls. On `dangeresque merge`, before `git worktree remove` runs (`mergeWorktree` in `src/worktree.ts:545-567`), the CLI copies the issue's artifact directory from `<worktree>/.dangeresque/runs/issue-N/` to `<projectRoot>/.dangeresque/runs/issue-N/`. On `dangeresque run`, before spawning the worker, copy any existing `<projectRoot>/.dangeresque/runs/issue-N/` into the new worktree so the worker sees prior runs.

**Pros:**
- Symmetry with `.dangeresque/sessions/` (already gitignored at `.gitignore:6`) — exactly what the issue asks for.
- Zero footprint in git history. No retroactive scrub needed for new repos.
- Preserves `results --issue` and `stats` (they read from local FS, not git).
- Worker prompt unchanged — it still finds prior runs at the documented path.
- Reviewer prompt mention of "exclude .dangeresque/runs/" can be removed since runs are no longer in the diff.

**Cons:**
- **Loss of cross-machine portability.** A teammate cloning fresh has no run history. `git fetch` no longer carries it. Mitigation: optional `dangeresque export <N>` / `import` round-trip, or punt entirely (sessions today have no portability either, and nobody complains).
- Two new code paths (copy on merge, copy on dispatch) — both can fail and need clear errors.
- Race risk: if `dangeresque merge` fails after the copy but before the worktree removal, the artifact exists in two places. Acceptable — operator reruns merge.

**Touchpoints:**
- `src/init.ts:159-174` — invert logic: ensure `.dangeresque/runs/` is *in* `.gitignore`.
- `src/runner.ts:103-112` (`commitArchiveFile`) — delete or no-op.
- `src/artifact.ts:395-407` (`commitArtifactJson`) — delete or no-op.
- `src/runner.ts:131-157` (`commitWorkerChanges`) — already excludes `.dangeresque/runs`; can stay.
- `src/worktree.ts:456+` (`mergeWorktree`) — add Phase 0: copy artifacts out before worktree removal.
- `src/runner.ts:637+` (`runWorker`) — before mkdir, copy `<projectRoot>/.dangeresque/runs/issue-N/` into the new worktree if it exists.
- `src/cli.ts:485` and `src/summary.ts:48` — drop the `.dangeresque/runs/` exclude (no longer in diff anyway).
- `src/runner.ts:497` reviewer prompt line — drop the exclude language.

### Proposal A2 — orphan branch for runs (`dangeresque-runs`), never pushed

**The change:** keep run artifacts under git but on a dedicated orphan branch (`dangeresque-runs`), separate from `main`. Worker writes locally; instead of committing to the worktree's branch, the merge step (or a post-worker hook) commits the artifact onto the orphan branch from the main checkout. Add a pre-push hook (or document the rule) that refuses `git push dangeresque-runs`. Workers reading prior runs do `git show dangeresque-runs:.dangeresque/runs/issue-N/<file>` instead of reading from the working tree.

**Pros:**
- Preserves full audit trail in-repo, just not on `main`.
- Optional sharing: a team can push the branch to a private remote without exposing `main`.
- No file-copy logic needed — git handles dedup, history, blame.

**Cons:**
- Significant complexity: orphan branch initialization, push-blocking, atomic commit-to-other-branch from a worktree (requires `git --git-dir=… --work-tree=…` plumbing or a temp worktree).
- Still leaks if a careless `git push --all` runs. The push-block has to be airtight to be trustworthy.
- Worker prompt has to change ("read prior runs from `git show dangeresque-runs:…`") — bigger UX churn.
- `stats` and `results` need a git-show layer instead of plain `readdirSync`.
- Doesn't satisfy the issue's "similar to .dangeresque/sessions" framing.

### Proposal A3 — encrypted-at-rest artifacts in git

**The change:** keep committing artifacts to `.dangeresque/runs/` exactly as today, but encrypt the body with AES-256-GCM keyed off a project-local secret stored at `~/.dangeresque/keys/<project-hash>.key` (gitignored, outside repo). Worker writes plaintext to disk transiently; pre-commit step replaces the file with an `.enc` (or just opaque base64-in-`.md`) ciphertext. Reader functions (worker prompt context, `results`, `stats`) decrypt on the fly.

**Pros:**
- Preserves exact current portability: clone, push, pull all keep working.
- A leaked GitHub repo without the key reveals only ciphertext metadata.
- Audit history intact. No file-copy / orphan-branch plumbing.

**Cons:**
- **Key management is the whole game.** Lose the key → lose all history. Share the key → re-introduce the leak through a different channel. macOS Keychain integration is the right home but adds a real cross-platform problem (Linux dangeresque also exists per `src/config.ts:200-202`).
- Encrypted blobs in `git diff` are noise; PR review of dangeresque-itself becomes harder.
- The JSON artifact (`stats` consumer) now needs a decrypt path everywhere it's read.
- Doesn't actually match what the issue asks for ("similar to how `.dangeresque/sessions` works" — i.e., gitignored).

## Proposals — GitHub comment leak

### Proposal B1 — Post the SUMMARY block only, never the full body

**The change:** rewrite `postRunComment` (`src/runner.ts:928-972`) to extract the `<!-- SUMMARY -->...<!-- /SUMMARY -->` block via the existing `parseSummaryBlock` (`src/worktree.ts:321-326`) and post just that, plus a path reference like `Local artifact: .dangeresque/runs/issue-57/2026-04-30T03-56-36-INVESTIGATE.md`. Failure-path comment can stay as-is (it never contained body) or shrink further.

**Pros:**
- The SUMMARY block is *already* the designed-for-machine-parsing redaction surface (worker-prompt explicitly tells workers to put compressed status info there, no source quotes). Using it here is the obvious fit.
- Tiny diff: one function, ~20 lines. No config surface to debate.
- Stakeholders watching the issue still get a "what happened" pulse.
- Pairs cleanly with any A-proposal — even if artifacts stay in git, GitHub stops echoing the body.

**Cons:**
- Reviewers who currently scroll the GitHub issue to read findings have to switch to `dangeresque results --issue N`. UX regression for that habit.
- A poorly-written SUMMARY block can still leak (worker types a code snippet into it). Mitigation: keep the worker rules note that SUMMARY is the public surface — already implied, would be made explicit.

### Proposal B2 — Make commenting opt-in via config (`postRunComment: "off" | "summary" | "full"`)

**The change:** add a `postRunComment` field to `DangeresqueConfig` (`src/config.ts:42-71`). Default to `"summary"` for new projects (B1 behavior). `"off"` skips entirely. `"full"` preserves today's behavior for users who actively want it. Failure-path comment respects the same setting.

**Pros:**
- Backwards-compat preserved for anyone whose workflow depends on the issue thread.
- Gives users an audit-vs-privacy dial. Public-repo defaults can ship as `"summary"`, private-repo workflows can opt into `"full"`.
- Aligns with `notifications: boolean` (`src/config.ts:62`) — same pattern of "thing dangeresque does on your behalf, gateable in config."

**Cons:**
- Three modes → three test paths. Slightly more code than B1.
- Default-summary still surprises users on upgrade — needs a one-time changelog/release note.
- "Off" means the only audit trail is the local artifact file; if a user picks `off` *and* picks an A-proposal that gitignores artifacts, they have no remote audit trail at all. Acceptable but worth documenting.

### Proposal B3 — Post a link to a private GitHub Gist instead of inline content

**The change:** on success, push the artifact `.md` to a private (secret) Gist via `gh gist create`, then post a comment like `**[dangeresque INVESTIGATE]** artifact: <gist-url>`. Operator + repo collaborators with read access to the gist can click through; drive-by readers can't.

**Pros:**
- Preserves the "click in GitHub to see the writeup" affordance — closest UX to today.
- Content lives off the issue thread and out of the repo's git history.
- `gh gist create` is already in the `gh` CLI we already require.

**Cons:**
- Secret gists are *unlisted, not private* — anyone with the URL can read. The URL must never be posted publicly. Posting it as an issue comment defeats the purpose on a public repo. **This proposal only works on private repos.** That's a footgun.
- Adds a new external surface (gist account, deletion lifecycle, rate limits) to manage.
- Gist deletion semantics: when the issue is closed or the run is discarded, who deletes the gist? If never, you accumulate gists forever.
- Doesn't help if the threat model is "anyone-with-issue-read-access" since they can usually click the gist link too.

## Recommended combination

If forced to pick, I'd ship **A1 + B1**:

- **A1** matches the issue's phrasing ("similar to how `.dangeresque/sessions` works") exactly. The cross-machine portability loss is real but the same loss already applies to `.dangeresque/sessions/` and nobody has filed an issue about it. The codebase already has the precedent and the muscle (`commitWorkerChanges` already excludes `.dangeresque/runs` — half the work is wired).
- **B1** is the smallest, lowest-risk, most-aligned-with-existing-design change. The SUMMARY block was *engineered* as the redaction-friendly surface. Use it.

A1+B1 together close both leak vectors while leaving the "worker → reviewer → human-merge" loop unchanged externally.

## Risks / Uncertainty

- **Migration story for existing projects.** Repos that already have `.dangeresque/runs/` committed will keep their history (gitignore doesn't unstage). Need a one-time `git rm --cached -r .dangeresque/runs/` doc step, or a `dangeresque init --migrate` flag. Not in scope for #57 but worth flagging.
- **Test fixture updates.** `test/unit/runner.test.ts` uses real `execSync` + scratch dirs (per CLAUDE.md). Behavior tests that assert on commits over `.dangeresque/runs/` will break. Manageable.
- **CHALLENGE-IN-WRITING:** the issue title says "find a better way to deal with artifacts" and the body says "3 proposals for workarounds for both of these issues" — so this run intentionally stops at proposals. If the reader was hoping for a single recommended path, see "Recommended combination" above; A1+B1 is the strongest pairing.
- **Out of scope but adjacent:** `.dangeresque/sessions/` (the JSONL transcripts) is gitignored today but is *not* redacted on disk — same plaintext-on-host as runs would be. If the threat model is "compromised local machine," neither A1 nor B1 helps. If the threat model is "public git history + public issue thread," A1+B1 is sufficient.
