# Summary

The staged plan is structurally correct. The three root causes hold up at the cited lines. The biggest gap the diagnosis didn't fully surface is that **`writePidFile` tracks the *engine child* PID, and engines are spawned without `detached: true`** — so SIGTERM to the tracked PID kills the engine but (a) leaves any grandchildren orphaned and (b) does NOT stop the dangeresque CLI parent, which will then spawn the review pass on top. `dangeresque stop` needs a strategy for both layers, not just the engine.

### G1. Root causes

### G2. PID target — engine child or CLI parent?
**Engine child only.** `writePidFile` callers (all in src/runner.ts):
- src/runner.ts:635 — codex worker `spawn("codex", …)` returns `child`, then `writePidFile(worktreePath, child.pid, { engine: "codex", workerLogPath, archivePath })`.
- src/runner.ts:689 — claude worker, same pattern (3-second `setTimeout` delay; see G6 below).
- src/runner.ts:750 — codex review, replaces with review child PID.
- src/runner.ts:792-793 — claude review, writes then immediately `updatePidFile`s with the same field (the second call is redundant — flag for cleanup but out-of-scope here).

The dangeresque CLI parent's `process.pid` is **never recorded**. Implication for `dangeresque stop`: killing the tracked PID terminates only the engine. The CLI parent in `cmdRun` is awaiting `runWorker`'s promise; when the engine exits, `child.on("close")` fires, `runWorker` resolves, and the parent proceeds to call `runReview` (src/cli.ts:492) — spawning a *new* engine. **Stopping the engine alone does not stop the run.** `stop` must either (a) also kill the parent, or (b) leave behind a sentinel that `cmdRun` checks before spawning review, or (c) the parent must trap SIGTERM and propagate.

### G3. Process group / detached
**No `detached: true` anywhere.** Verified via grep — zero matches for `detached` in `src/`. All four `spawn()` call sites use the default (`detached: false`):
- src/runner.ts:615 — `spawn("codex", args, { cwd: worktreePath, stdio: ["pipe","pipe","pipe"], env })`
- src/runner.ts:676 — `spawn("claude", args, { cwd: opts.projectRoot, stdio: useStdin ? [...] : "inherit", env })`
- src/runner.ts:729 — codex review (same shape as worker)
- src/runner.ts:780 — claude review (same shape as worker)

Consequence: the engine inherits the dangeresque CLI's process group. `process.kill(-pid, 'SIGTERM')` on the *tracked* PID does NOT translate to a clean process-group kill — that PID is not a process group leader. To enable cascade-kill of the engine plus its bash/tool grandchildren, runner must spawn with `detached: true`. Without that, `dangeresque stop` will leave orphaned tool subprocesses (e.g., a stuck `Bash(git fetch)` the AI was running).

### G4. Stale PID files & PID reuse
**Liveness check is adequate; PID-reuse risk is real but small enough to ignore.**
- worktree.ts:160-165 uses `process.kill(pidInfo.pid, 0)` — signal 0 is a no-op probe, throws ESRCH if PID doesn't exist (treated as not-running) and EPERM if it exists but unowned (treated as not-running by the bare `catch`). EPERM as "not-running" is technically wrong but irrelevant in our single-user CLI context.
- PID files are removed on clean child exit at every spawn site (src/runner.ts:651, 694, 699, 761, 767, 797, 802). They only linger after a hard kill (SIGKILL) or crash.
- PID-reuse risk: a stale file persists, the PID gets recycled by an unrelated process, gates think the worker is alive. In practice: PID space on macOS is ~99,999 and Linux ~32k by default; recycle takes minutes at minimum on a quiet system. The user-visible failure mode is "gate refuses, says 'pid X running for 4 hours' which is obviously wrong" — at which point `--force` is the escape hatch. **Verdict: keep the existing `process.kill(pid, 0)` check. Optional hardening: cross-check `pidInfo.startedAt` against `ps -o lstart` for the PID; out of scope unless we hit it in the wild.**

### G7. Does `mergeWorktree` already fail naturally on running worktrees?
**Partially, and unreliably.** Phase 1 (`git merge ${branch}` from main, worktree.ts:438) doesn't care about live processes — git allows merging a branch checked out in another worktree. Phase 2 (`git worktree remove "${worktreePath}"` *without* `--force`, worktree.ts:490) refuses if there are uncommitted modifications, but:
- A worker that's just started or between edits has no modifications → cleanup may succeed and yank the worktree out from under the live process.
- A worker mid-edit fails Phase 2 → user sees "Merge succeeded — main is now at … Worktree cleanup failed" and is left with main moved AND the live worker still going. This is exactly the "weird behavior" the issue describes, only in the merge path.

**An explicit PID gate is required.** Don't rely on the modification-status side-effect.

### G8. Layer 2 invariant — `rev-list --count` vs `merge-base --is-ancestor` + no-remote behavior
**Use `git rev-list --count origin/HEAD..HEAD > 0`.** Rationale:
- The existing `checkRemoteBehind` (runner.ts:524) already uses this exact form. Reusing it keeps semantics identical and avoids subtle drift between the warn (Phase 0) and the block (Phase 2).
- `merge-base --is-ancestor origin/main main` only tells you ancestry direction. For the "is local ahead of origin" question, `rev-list --count` is more direct and gives the count for the error message ("local main is N commits ahead of origin").
- Use `origin/HEAD` not `origin/main` — `origin/HEAD` resolves to whatever the remote default is (master/main/trunk), which is more portable. `resolveDiffBase` (worktree.ts:22-36) already handles the no-symbolic-ref fallback to "main".

**No-remote behavior:** when `git symbolic-ref refs/remotes/origin/HEAD` fails (no `origin` remote, or no remote HEAD set), the gate should **silently noop**. Match the existing `checkRemoteBehind`'s try/catch (runner.ts:533-535). Don't warn — there's nothing to be ahead *of*. Local-only repos are a legitimate dangeresque use case (init's brief mentions offline). The same goes for Phase 1: discard/merge gates need only the PID check; they don't depend on remote.

### G9. `extractIssueNumber` (src/worktree.ts:385) — correct for all current branch shapes?
**Yes for all production-shaped branches; theoretically loose but practically safe.** The regex `/-(\d+)$/` matches the trailing digit run. Test coverage in test/unit/worktree.test.ts:20-26 confirms:
- `worktree-dangeresque-investigate-63` → 63 ✓
- `worktree-foo-bar` → undefined ✓ (no trailing digits)

Edge case: when the user runs `dangeresque run` without `--issue` (impossible in current `cmdRun` — it errors at src/cli.ts:281-290) we'd never hit this. Auto-naming `${Date.now()}` produces `worktree-dangeresque-1709310000000` whose 13-digit "number" would never collide with a real issue N. **Safe for Phase 2's "any worktree for issue N" check.** Hardening (anchoring to known mode prefixes) is not required.

### G10. `dangeresque stop` and the review pass
- The PID file is overwritten when review starts (runner.ts:750-757 codex; 792-793 claude). At any moment, only one PID is tracked. So `stop` always targets "whatever is currently running".
- BUT — and this is the critical issue — the dangeresque CLI parent drives the worker→review sequence inside `cmdRun` (src/cli.ts:353-505). Killing the engine alone doesn't stop the parent: `runWorker`'s promise resolves with `exitCode != 0` (signal-killed), the parent moves to the post-worker scope check (src/cli.ts:425-457), then to rebase + review. It will spawn a new engine for the review pass.

  **Wait** — actually look more carefully at src/cli.ts:384-422: if `workerResult.exitCode !== 0` the parent prints the FAIL banner and `process.exit(workerResult.exitCode)`. Signal-killed processes return non-zero exit codes. So killing the engine *will* cascade into a parent exit, by accident. But this is fragile:
  - Codex's `child.on("close")` returns the OS signal as `code === null` → `code ?? 0` makes it 0 (runner.ts:660). **Killing codex would resolve as exitCode=0, parent proceeds to review.** Bug.
  - Claude's path (runner.ts:704) has the same `code ?? 0` collapse. Same bug.

  So the current "kill the engine" path is more broken than the diagnosis claims — for a SIGTERM-killed engine, the parent thinks it succeeded and spawns review. The IMPLEMENT phase has two paths:
  - **A (minimal):** `stop` writes a sentinel file (e.g., `<worktree>/.dangeresque/stopped`); `cmdRun` checks for it before spawning review. Cheap. Doesn't solve the "scope check + rebase still run on partial output" issue.
  - **B (correct):** Track the parent PID in PidInfo (new field `cliPid?: number`). `stop` kills parent first (SIGTERM with a CLI signal handler that propagates to the engine and skips review), then engine pgid as a backstop. Requires runner to spawn engines with `detached: true` so the engine pgid kill is safe.

  **Strong recommendation: option B.** The minimal sentinel-file approach (option A) leaves the run in an even weirder state. If the IMPLEMENT phase wants to ship Phase 1 fast, an interim ship of A is acceptable, but B should be the eventual target.

### G11. `--force` semantics — single flag or split?
**Single `--force` overriding both Phase-1 and Phase-2 gates.** Reasons:
- The mental model is "I know what I'm doing, get out of my way." Splitting flags adds memorization burden.
- The orchestrator (an LLM) reads natural language, so the failure message can name *which* gate `--force` would override and the operator can decide.
- If a real need to split emerges later (e.g., the orchestrator wants to tolerate stale main but not silently kill workers), add `--force-running` and `--force-stale` then. YAGNI for now.

For `discard`, the issue's plan says `discard --force = stop + discard chained`. That's a bigger semantic shift (running side-effect: kills a process). I'd surface this as: **if `discard --force` finds a live PID, it implicitly invokes `stop`'s logic (SIGTERM→wait→SIGKILL→clear PID), then discards.** Fine. Just make sure the help text and the error-on-no-force ("worktree is running, use `dangeresque stop` first or `dangeresque discard --force`") spells out both routes.

# Observations (not in scope, do not fix here)

1. **`updatePidFile` immediately following `writePidFile` at runner.ts:792-793** is dead code — they write the same fields. Worth a one-line cleanup during IMPLEMENT.
2. **Codex/claude worker `code ?? 0`** at runner.ts:660 and 704 collapses signal-kills (where `code === null`) into exitCode=0. This means the parent CLI treats a stopped worker as success and proceeds to review. Critical for `stop` design (see G10). The right fix is to map `code === null && signal !== null` to a non-zero exit (e.g., 128 + signal number, the POSIX convention).
3. **Claude worker's 3-second `setTimeout` PID write** (runner.ts:687-691) leaves a 3-second window where no PID file exists. During this window, `dangeresque stop`/`status`/`logs` would all report "no PID". The codex path (runner.ts:634) writes immediately. Inconsistent. Likely safe to drop the setTimeout.
4. **`disallowedTools` defaults already include `Bash(git branch -D *)`** (config.ts:101). The new `dangeresque discard --force` and `dangeresque stop` commands run from the dangeresque CLI parent (not inside the AI worker), so this disallow doesn't bind them. But future workers running `dangeresque` recursively (unlikely) would be blocked. Note for awareness only.

# Open design questions for IMPLEMENT

These are the decisions IMPLEMENT must take before writing code. Brief grammar; sacrifice form for clarity.

1. **`stop` strategy: option A (sentinel file) or B (track parent PID + spawn engines `detached:true`)?** Recommend B; A is acceptable as interim if scope-pressed. Either way, *also fix* the `code ?? 0` signal-kill bug at runner.ts:660/704 so the parent observes a non-zero exit when the engine is signal-killed.
2. **Does `mergeWorktree`'s Phase 1 gate also block on stale main?** Issue plan says Phase 2 gate is on `run`. But merging a worktree onto a main that's behind origin produces a local main further from origin — fine for local, but prone to losing track. Recommend: Phase 1 gate on `merge` is *running-only*; Phase 2 stale-main is *run-only*. Don't conflate.
3. **`dangeresque stop` + `dangeresque discard --force` + `dangeresque kill` — same command surface or layered?** Issue plan: `stop` is a new command, `discard --force` chains `stop` + `discard`. No `kill`. OK as-is. Just be sure the help text in `cli.ts:46-98` (`usageForEngine`) lists `stop` and the new `--force` flag.
4. **Exit code 2 for gate refusals — only for `discard`/`merge`/`run` gates, or also for `stop`?** Issue plan says exit 2 for gate refusals in general. `stop` succeeds when the process is dead (or gets killed); it's not a "gate". Recommend `stop` returns 0 on kill, 1 on internal error, no exit 2. `discard`/`merge`/`run` use exit 2 for "gate refused; fix workflow and retry".
5. **What if PID file is missing but worktree directory exists?** Three cases: (a) older run that predates PID tracking, (b) worker crashed and left no PID file, (c) PID file manually deleted. The gate should treat "no PID file" as "not running" — same as today's `readPidState` (worktree.ts:155 returns `{ running: false }`). No change needed; just confirm in tests.
6. **PID file path collisions inside the same worktree.** `PID_FILE` is `.dangeresque.pid` (config.ts:8) at the worktree root. Worker and review both write to the same path. Fine for the current "one engine at a time" model. If we ever run worker+review concurrently this breaks — flag for future.
7. **Engine flag for `detached: true` requires terminal not to inherit stdio.** Claude's interactive path uses `stdio: "inherit"` (runner.ts:678) — incompatible with `detached: true` for full pgid isolation. Headless path uses `["pipe", "inherit", "inherit"]` — same issue with stderr/stdout. The IMPLEMENT phase will need to either (a) detach only on headless, (b) capture all three streams and re-emit, or (c) accept the limitation and only enable pgid kill on codex (which already pipes everything). Decide explicitly.
