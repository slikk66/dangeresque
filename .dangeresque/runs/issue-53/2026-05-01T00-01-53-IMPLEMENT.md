SIGTERM to parent CLI + engine in parallel, 5s grace via `waitForExit` polling, SIGKILL survivors, then `process.kill(-pid, "SIGKILL")` engine pgid as a backstop for tool grandchildren. - **`discardWorktree` and `mergeWorktree` PID gates** at `src/worktree.ts:456-481` (merge) and `src/worktree.ts:619-657` (discard). `readPidState` now considers liveness OR-of-engine-and-parent so the gate fires through worker→review transitions. - **`discard --force`** at `src/cli.ts:802-838`. Picker filter widens to `"all"` under `--force` (otherwise keeps the long-standing `"finished"` UX hint, since the in-function gate is the real check). Force chains through `stopWorktree` then proceeds to phase-1 cleanup.

# Risks / Uncertainty

1. **Headless claude with `stdio: ["pipe", "inherit", "inherit"]` plus `detached: true`** is a first-time configuration. The pipe-half (stdin) is private to the child, but the inherit-halves (stdout/stderr) keep the child coupled to the parent's terminal handles. On non-Windows, detaching still creates a new process group, so `process.kill(-pid, "SIGKILL")` for pgid-cascade should work. If we observe orphaned tool subprocesses after a `dangeresque stop` against a claude headless run, the fix would be to capture all three streams via pipes and re-emit (which the codex paths already do).
2. **No live engine integration test.** The unit suite uses `process.pid` and `node -e "setInterval(...)"` for liveness fixtures. End-to-end behavior with a real claude/codex spawn under SIGTERM has not been exercised. A VERIFY pass against a deliberately-stopped real run would close this.
3. **PID-reuse window on the cliPid recheck.** `isPidAlive(pidInfo.cliPid)` uses `process.kill(pid, 0)` which only checks for an existing process — not whether it is the *same* process that started the run. On long-idle stale PID files the OS could recycle the PID. The investigation deemed this an acceptable risk given the user-visible failure mode (gate refuses with an obviously-wrong "started 4h ago" elapsed time → operator uses `--force`). Hardening would cross-check `pidInfo.startedAt` against `ps -o lstart`; deferred unless we hit it in the wild.
4. **Stop interrupts mid-`postRunComment`.** Stop sends SIGTERM to the parent; the parent's signal handler does NOT exit immediately — it kills engines and lets cmdRun's natural fail path run. With the new `stopRequested` check, the post-fail GitHub comment is skipped, but the FAIL banner still prints, the artifact is still finalized, and `process.exit(143)` is called normally. If the operator's stop uses SIGKILL directly (or stops races with a slow GitHub call), the parent dies mid-flow and the PID file may linger. The next `dangeresque stop` cleans it up; this is acceptable.
5. **`--force` semantics in `cmdDiscard` widening the picker filter to `"all"`** is a soft UX change (with `--force`, running worktrees appear in the picker; without, they're hidden as before). The brief did not specify picker behavior; the choice is local. If the orchestrator never uses the picker, this is a no-op for it.
